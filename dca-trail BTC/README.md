# DCA-Trail — усреднение на просадках с единым трейлинг-ТП

Стратегия усреднения (martingale/DCA): бот постепенно докупает позицию на
внутричасовых просадках и держит **один** трейлинг-стоп на весь накопленный
объём, вместо TP/SL на каждую отдельную покупку.

## Идея

- Нет фиксированного входа "одна сделка = один TP/SL". Позиция наращивается
  по частям, пока рынок падает.
- Точка отсчёта для просадки — **open текущего часа** (1H-свеча), а не 24h,
  как в соседней стратегии `buy-the-dip-trail`.
- Как только позиция открыта (`pos > 0`), на неё всегда висит один
  trailing take-profit на **весь текущий объём**. Если объём вырос
  (докупили ещё) — старый трейлинг-ТП снимается и переставляется на новый,
  уже увеличенный объём.

## Машина состояний (на каждый инструмент, каждый цикл)

```
[1] pos > 0?
    ├── нет trailing TP        → ставим trailing TP (activate >= entry+tp_activate_pct%,
    │                             дальше следует за ценой с callback = trailing_tp_callback_pct%)
    │                             на весь pos
    └── trailing TP есть,
        но его sz != текущему pos → отменяем и переставляем на новый pos

[2] Цена относительно open текущего часа
    ├── просадка <= hourly_dip_threshold_pct
    │     ├── нет активного trailing BUY, покупки в этом часу не было,
    │     │   И (позиции ещё нет ИЛИ цена < средней цены позиции)
    │     │     → ставим trailing BUY (сумма = buy_size_usd, gap = entry_trail_callback_pct)
    │     ├── trailing BUY уже есть            → пропускаем (лимит: не более 1 активного на инструмент)
    │     ├── покупка в этом часу уже была     → пропускаем
    │     └── цена >= средней цены позиции     → пропускаем (не усредняемся вверх)
    └── просадки нет → ничего не делаем
```

Оба шага независимы и выполняются в каждом цикле: даже если позиция уже
открыта, бот продолжает искать возможность доусредниться, пока не наступит
новая часовая просадка.

**Не более одной покупки за час.** Ограничение "1 активный trailing BUY"
само по себе не защищает от повторной покупки в том же часу: если ордер
исполнился, `hasTrailBuy` снова становится `false`, и при продолжающемся
падении бот мог бы поставить второй trailing BUY в тот же час. Чтобы этого
не происходило, бот запоминает часовой bucket (`floor(unixtime/3600)`),
в котором был выставлен trailing BUY, и не ставит новый, пока не наступит
следующий час — даже если предыдущий уже исполнился или был отменён.
Это состояние хранится только в памяти процесса и сбрасывается при
перезапуске скрипта.

**Не усредняемся вверх.** Если позиция уже есть, новый trailing BUY
ставится только когда текущая цена ниже средней цены позиции (`avgPx`).
Это не даёт боту докупать по цене выше уже набранного среднего — усреднение
идёт строго вниз, что и есть смысл DCA-стратегии.

## Параметры конфига (`config.json`)

| Поле | Описание | Пример |
|---|---|---|
| `instruments` | Список инструментов | `["BTC-USDT-SWAP", ...]` |
| `hourly_dip_threshold_pct` | Порог падения от open текущего часа, при котором ставится trailing BUY | `-1.0` |
| `entry_trail_callback_pct` | Гэп (callback) трейлинг-стопа на вход | `0.5` |
| `buy_size_usd` | Сумма одной докупки в USD (до применения плеча) | `1` |
| `leverage` | Плечо | `8` |
| `mgnMode` | Режим маржи | `isolated` |
| `trailing_tp_callback_pct` | Гэп (callback) единого трейлинг-ТП на весь объём позиции — на сколько % цена должна откатиться от своего пика, чтобы сработала продажа | `2.0` |
| `tp_activate_pct` | Порог активации трейлинг-ТП: % прибыли от средней цены входа (`avgPx`), после которого трейлинг вообще начинает отслеживать откат. `0` или не указан — трейлинг активен сразу после постановки ордера (риск продажи около входа при слабом росте) | `1.0` |
| `log_file` | Путь к CSV-логу сделок | `.\trades.csv` |
| `rerun_interval_s` | Пауза между циклами, сек | `5` |
| `dryRun` | Если `true` — POST-запросы (ордера) не отправляются, только логируются | `true` |

Просадка часа считается через `open` текущей (ещё не закрытой) 1H-свечи
(`/api/v5/market/candles?bar=1H&limit=1`). Значение кэшируется на весь час
для каждого инструмента, чтобы не дёргать API каждый цикл — обновляется
автоматически при переходе на новый час.

На самой границе часа OKX иногда ещё отдаёт предыдущую (уже закрытую)
свечу как "последнюю", пока новая не создалась на их стороне. Скрипт
сверяет timestamp полученной свечи с ожидаемым часом и **не кэширует**
значение, если они не совпадают — иначе просадка весь час считалась бы от
устаревшего open предыдущего часа. При несовпадении бот просто пробует
получить свечу заново на следующем цикле.

## Запуск

```powershell
.\trade.ps1              # dryRun режим (по умолчанию в config.json)
.\trade.ps1 -ForceLive   # боевой режим — реальные ордера
.\trade.ps1 -DebugMode   # подробный вывод запросов/ответов
```

Перед первым боевым запуском проверьте `config.json`: `dryRun: true` —
это осознанная настройка безопасности, переключайте на `false` (или
используйте `-ForceLive`) только когда логика проверена по логам.

## Защита от дублирующих trailing TP ордеров

Изначально бот мог выставить несколько активных trailing TP на один и тот же
объём позиции. Причины и защита:

1. **`GET /orders-algo-pending` неотличим от сбоя.** Если запрос не удался
   (сеть, rate-limit), скрипт раньше трактовал это как "ордеров нет" и ставил
   новый TP поверх уже существующего. Теперь неудачный запрос даёт `$null` и
   весь цикл для инструмента пропускается — не путается с "ордеров
   подтверждённо нет".
2. **PowerShell разворачивает `return @()` в ноль объектов.** Из-за этого при
   `$x = Get-ActiveAlgoOrders ...` пустой список ордеров тоже превращался в
   `$null`, из-за чего пункт 1 срабатывал каждый раз, когда активных ордеров
   действительно не было — то есть почти всегда. Функция теперь возвращает
   `,@()` (оператор запятой защищает от разворачивания в пайплайне).
3. **Гонка при постановке/переустановке ТП.** После постановки или
   переустановки TP бот ждёт `tpChangeCooldownSec` (6 сек) перед следующим
   изменением — чтобы не среагировать на то, что новый ордер ещё не появился
   в списке активных на стороне биржи.
4. **Self-heal.** Если несмотря на всё это на инструменте всё же оказалось
   больше одного активного trailing TP — бот отменяет все и ставит один
   заново на актуальный объём позиции.

## Важно: не запускать параллельно с `buy-the-dip-trail` на тех же инструментах

Биржа не различает, каким скриптом выставлен `move_order_stop`-ордер.
Если этот бот и `../buy-the-dip-trail/trade.ps1` работают одновременно на
одном и том же инструменте, они будут видеть чужие trailing-ордера как свои
и правило "не более одного активного trailing BUY" сломается. Держите
списки `instruments` в конфигах непересекающимися, либо не запускайте
стратегии параллельно на одних и тех же парах.
